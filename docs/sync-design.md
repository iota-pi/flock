# Sync Design Notes

Background and rationale for the sync system (`packages/vault-client/src/{worker,client,shared,utils}/`, `packages/vault-server/src/services/`). [AGENTS.md](../AGENTS.md) lists the rules. This file explains why they exist. Read the relevant section before changing or reviewing sync behaviour.

## Data flow

```
User edit → Automerge doc change → pending mark → two outbound paths:
  1. Incremental: ChangeOutbox → getChangesSince(doc, serverHeads) → SyncPoller → log append → acknowledgement marks the item dirty
  2. Snapshot:    the last phase of the same poll: SnapshotPusher → push to the log first → server snapshot upload

Server → two inbound paths:
  1. Incremental: SyncPoller → SyncLogPuller → loadIncremental into the doc
  2. Full state:  a phase of the same poll, when due: ManifestSyncManager → calculateSyncDeltas → fetch snapshots → hydrate docs
     Targeted:    GapHealer (parked rows, missing local data) → ManifestHydrator.fetchSnapshots → hydrate docs, bypassing the deltas
```

The local Automerge doc in IndexedDB is always the complete, authoritative state. The log, snapshots and server rows are only delivery mechanisms. The server cannot decrypt anything, so it never merges or reconciles. It only relays data.

## Sync log

Each account has one strictly ordered log, the `FlockSyncLog` table, keyed by `account` and `seq`. `sync.pollLog` pushes messages and reads the log in one mutation.

### Server

- **Rows are contiguous.** Every committed push uses exactly the next seqs, and a failed push uses none. One `TransactWriteItems` updates the head row (`seq: 0`, with the condition `head = :expected`) and puts each message, so a transaction for seqs `e+1…` can commit only after the one for `…e`. The head row isn't on the `FlockAccounts` record, because `extendSession` writes that when it renews a session (once it has under 48 hours left, so about daily), and a write to an item in a running transaction fails. All of an account's appends serialise on the head row, which is fine for one user's devices; a shared account would need a sub-log per device.
- **Reads are consistent `Query`s on the base table,** strictly `seq > after`, with no GSI, page token or lookback. DynamoDB documents `Query` as read-committed, which may show some rows of a multi-row transaction and not others. Contiguity makes that harmless, because the client never moves past a missing seq it might still see.
- **A row's `encryptedMessage` is a run of Automerge change chunks** encrypted with the item's ID. There's only one kind of row, and an item's change set can span several rows, in dependency order.
- **Rows expire after `SYNC_LOG_TTL_DAYS` (30).** Snapshots are the lasting copy (see "Snapshot coverage").

### Outbound: from the doc

There's no write-ahead log and no sync protocol against a pretend peer. The doc is the only copy of a change, so nothing can be pruned, compacted or stuck in flight.

- **Server heads** (`ItemSyncState`, stored in each item's sync record) are heads whose every ancestor is on the server, in the log or in the item's current snapshot. They must be heads the doc has: `getChangesSince` returns the whole history, without throwing, for heads it lacks. A snapshot this device merges (`onItemSnapshotHydrated`) or already holds (`onSnapshotCovered`) moves them to the frontier of their old value and the snapshot's heads (`ItemSyncState.advanceServerHeads`), never back: a stale snapshot, such as one uploaded by a device that hadn't seen this device's pushed rows (the race S2 guards), would otherwise make the next push resend everything after it. Both sets are on the server with their ancestors, and the doc holds both once it has merged the snapshot, so the frontier is too. An item with no server heads takes the snapshot's, and one whose doc isn't loaded keeps its own.
- **A pending mark** (`ChangeOutbox`) says an item may have changes after its server heads. It's a hint, and a false one costs an empty check. Each item has its own record, `{ itemId, tick, createdAt, blocked? }`, in the sync log database, so tabs never race on a shared value, and followers write marks too, so an edit survives a leader that crashes before pushing. A mark clears only if its tick is still the one the push read, in one IndexedDB transaction. A new mark keeps the old one's `createdAt` (when the item first had changes waiting), so a stuck item's age shows however often it's edited. When the leader's push skips an item for a reason only it knows (`snapshotOnly`, or `unloadable` for a doc that won't load), it records that as `blocked` on the mark, so every tab can count it.
- **A change from a follower can reach the leader after its mark is cleared:** the leader pushes, finds nothing and clears the mark, and only then does the doc change arrive. So the leader checks every doc change (`ChangeOutbox.onDocChanged`) and marks whatever it finds unpushed. The engine, not the app, listens for those changes: `AutomergeRepoManager` keeps one change listener (`DocChangeListeners`) on every item handle the Repo holds, whether the doc store found or created it or the Repo created it for a doc another tab sent, so the check doesn't depend on which items the app subscribes to. automerge-repo declares a `document` event for new handles but doesn't emit it, so the doc store reports the handles it gets and the broadcast adapter reports each doc it receives a message for.
- **Push** (`ChangeOutbox.pushItems`, leader only) reads `getChangesSince(doc, serverHeads)` under the item lock, groups the changes in order into rows of at most `MAX_INCREMENTAL_MESSAGE_BYTES`, and encrypts each row. Once the server has acknowledged every row of an item, its server heads become the heads the changes were read at, the item becomes dirty (it owes a snapshot), both in one save of its sync record, and then its mark clears if its tick hasn't moved. If that save fails, the marks stay and the save is retried: the heads are unsaved in memory, so a later push finds nothing to send, and it keeps the mark until a save has stored them (`ItemSyncState.hasUnsaved`). A crash meanwhile resends the changes, which Automerge ignores, and the acknowledgement marks the item dirty again. Those are always heads the doc had at one moment, so they stay a frontier. A lost acknowledgement or a partial failure resends the same changes, which Automerge ignores as duplicates.
- **One exchange at a time.** Pushes come from polls (snapshot uploads among them) and from rewrites, and each `pollLog` also reads the log, so `LogExchange` runs them one by one. An acknowledgement is recorded before the entries that came with it are applied, so that a pull sees the item as no longer pending.
- **A single change over the row limit** can't be split. The item takes the snapshot path (`snapshotOnly`), and its server heads become the snapshot's heads once it's confirmed. Other devices get the change at their next manifest sync, or sooner if a later row depends on it. A snapshot over the item limit goes to `recreateOversizedItem`.
- **Rows the server refuses** (400, 413 or 422, not an auth error or an outage) go the same way. `pushItems` retries a refused request one item at a time, and an item the server still refuses on its own becomes `snapshotOnly`. Otherwise one such item would fail every push for good. If its snapshot is refused too, `SnapshotPusher` quarantines it as usual.
- **`snapshotOnly` is kept in the item's sync record** until a stored snapshot confirms it, so a reload doesn't rediscover it with a failed push. The item is dirty as well (both are set together and saved in one transaction), and the startup and promotion audit queues a `snapshotOnly` item that somehow lacks its dirty flag too, so its snapshot is still asked for after a reload.

### Inbound: `SyncLogPuller`

For each entry, in seq order: check contiguity, skip an own echo, decrypt, apply, then advance the cursor. The cursor is saved debounced, and only once `repo.flush` has written the docs its rows were applied to, so a stored cursor never covers a change the device didn't store (rule 1). If a doc fails to save, the stored cursor stays behind and those rows are applied again.

- **Own echoes** are seqs this device pushed, kept in a bounded set. They only advance the cursor, and they don't count as "another device" for clearing a `pullDecryption` quarantine.
- **Decryption always comes first.** `loadIncremental` applies what it can of truncated or garbage bytes rather than throwing, so AES-GCM authentication is what rejects a damaged row.
- **`docStore.applyIncomingChanges`** applies a row under the item lock. A loaded doc takes `loadIncremental`. Otherwise the row goes through `Automerge.init()`: `Automerge.load` throws on a partial incremental, so a row with missing dependencies parks and no empty doc is stored, and the rest goes through `hydrateAutomergeDocumentBinary`, which merges into stored data and refuses to create a doc over it (rule 2).
- **Applying never marks an item pending.** Server heads follow the doc only if the item isn't pending and the doc matched them before the row. A doc that didn't has changes of its own, whose mark may not have reached storage yet, and moving the heads past them would mean they're never pushed. A pending item that pulls changes resends them once, which Automerge ignores, and its acknowledgement moves its heads past them.

`hasImmediatePendingPulls` is true only for `hasMore`. Waiting on a gap is never "immediate" (rule 4).

### Gaps

Where reading stopped (at a gap, with more pages, or neither) and whether it's catching up are one state value in `logPullState.ts`, moved by the pure `transitionLogPull`. Its spec is a table of transitions. The manifest syncs the puller needs (catch-up and recovery) aren't part of it: the puller places them as demands on `ManifestSyncManager` (`demand`), which decides every manifest sync, and a demand stays until a sync fetches the manifest.

A gap is a missing seq between the cursor and the next visible row.

- **Fresh gap.** The next visible row is under `gapWait` (30s) old by the server's clock (`serverNow − createdAt`), so the missing row may be part of a transaction that isn't fully visible yet. The cursor stays, and the orchestrator re-polls after 1s, 2s, 4s and so on, up to 16s. The poll still reports `'success'`.
- **Stale gap.** The next visible row is older than that, or a fresh gap has lasted that long. The row was lost, which can't happen by design, so the puller logs an error, moves past it and demands a manifest sync (`recoveryDemand`), which runs after the read at mode `now`, ignoring `manifestSyncMinGap`. Missing-dependency checks catch the items affected. The request stays until a manifest sync fetches the manifest: a poll whose sync couldn't fetch it fails (rule 4) and asks again next time.
- **Catch-up.** A device with no finished pull, or whose last one was more than `logCatchUpAge` (25 days) before `serverNow`, may be behind the TTL. It demands a manifest sync that runs before it reads (`catchUpDemand`), because the first visible row may still look contiguous. The poller asks the puller with the local clock before the first manifest phase, and `LogExchange` with the server's once it has a response: a page that shows the device is behind is dropped, because the manifest sync can't run inside an exchange. The phase after the read runs it, and the poll ends with more pages, so the log is read again at once. Until its first pull with `hasMore` false, a stale gap is expected, so it causes no error and no second manifest sync. Fresh gaps still wait.

### Parked entries and the `GapHealer`

An entry that can't be applied yet (a failed decryption, a missing key, missing dependencies or a doc that won't load) is parked and the cursor moves on. A parked entry keeps the row's ciphertext as it arrived, which the keyring can always read again, so it needs no seal, and it outlasts a reload rather than relying on Automerge's own queue of changes with missing dependencies reaching storage.

The `GapHealer` owns those items. It fetches an item's snapshot at once (`ManifestHydrator.fetchSnapshots`), re-applies its parked rows in seq order and checks for missing dependencies. Rows stay until nothing is missing. If the server doesn't have the dependencies yet, some device's doc does, and it retries after every later entry for the item, every manifest sync, every keyring update, and on a backoff (`GAP_HEAL_DELAYS`). Work runs at the end of each poll, so a failure fails the poll. That includes a snapshot fetch that fails as a whole; items whose snapshots can't be fetched or hydrated only wait for the next attempt.

- **After a day** (`missingChangesQuarantine`) of missing dependencies, or of a parked row that keeps failing to apply (a doc that won't load), the item is quarantined as `missingChanges`. It stays usable, keeps its rows and keeps retrying, and a heal clears the quarantine.
- **A row that won't decrypt** is dropped after `MAX_PULL_RETRIES` (5) and the item quarantined as `pullDecryption`.
- **A row waiting for a key** is never quarantined. A keyring update retries it.

The Repo has no peer to ask for a doc it can't find, so a find for an indexed item with no local data (after `replaceFromServer`, say) also goes to the healer.

### Poll result contract

`executePoll` returns `'success' | 'failure' | 'auth-failure' | 'no-poll'`, which drives `SyncOrchestrator` backoff:
- `'success'` resets backoff. Return it only when the whole cycle had no errors.
- `'failure'` triggers exponential backoff. Return it whenever push, pull processing, healing or the snapshot phase throws. The one exception is a 429 on `putSnapshots`, most likely the account's storage quota: the snapshot phase defers its uploads (`snapshotQuotaRetry`, 10 min) and the poll reports its own result, since pulls still work. No error that touches the pull path is swallowed.
- `'auth-failure'` pauses polling until a flush or restart, and tells the user the session has expired. Return it only when the server refused the session.
- `'no-poll'` leaves backoff unchanged, for example when the poll was aborted.

If any I/O throws and the poll still reports `'success'`, backoff resets while `hasImmediatePendingPulls()` stays true. The result is a 0ms re-poll loop.

The orchestrator's schedule is one state value (`idle`, `waiting`, `polling`, `authPaused`, plus the backoff attempt) moved on by `transitionPoll` in `pollSchedule.ts`, a pure function the orchestrator calls for every event; it only arms timers and runs polls. Its spec states this rule as named rows: a failure never schedules at 0ms, even with a flush pending or more pages to pull, and a gap never counts as immediate.

**A refresh that gets no answer is an outage, not an auth failure.** Nothing restarts paused polling, so a device that paused because it couldn't reach the server would stop contacting it for good. So `handleSessionExpired` reports `unreachable` for a network or server error, leaving the session and telling the host nothing, and `SyncApiClient` rethrows the network error the worker's refresh fails with. The poll returns `'failure'` and keeps retrying until the server answers. The same goes for a refresh the main thread never answers, which is every refresh during startup, because the bridge can't reach the worker until the session is ready. A login during an outage depends on this: it has no token, and `navigator.onLine` may well be true, so no `online` event will come. When a refresh restores a session that had been lost, the bridge runs its reconnect steps, because any request can be the one that gets it back.

## Snapshot coverage

Snapshot uploads stay unconditional last-write-wins, hydration still merges, and versions stay monotonic. Two rules (`ItemSyncState.isCovered`) keep every change in some snapshot, and make a snapshot that replaced another device's a superset of it again by the next manifest sync. That matters because a device that hydrates after the TTL has only snapshots to go on.

- **S1. Log before snapshot.** `SnapshotBuilder` builds a snapshot only when the doc has nothing after its server heads, checked in the same synchronous section as `Automerge.save`. Otherwise it returns `deferred`, and the caller pushes and builds again. So every change in a snapshot is already in the log. The one exception is a single oversized change.
- **S2. Backstop at manifest sync.** A device that holds a change must upload it if nobody else does. `ManifestSyncManager` marks an item dirty when its doc contains the server snapshot's heads and has other heads too. It checks snapshots newer than `baseVersion`, and items with pulled changes no snapshot has confirmed, which a device would otherwise never look at: their server version equals `baseVersion`. A pull that adds changes records when the item first had them (`pulledAt` in its sync record, kept by later pulls and stored before the saved log cursor can move past its rows), and after a day (`pulledChangesGrace`) the author has had its chance. A record goes once a snapshot's heads match the doc's, or once the manifest shows the item deleted, since a deleted item gets no more snapshots. A snapshot without heads (written before snapshots had them) can't be checked, so after the grace period the item is uploaded anyway; the new snapshot has heads, which confirm the record at the next manifest sync.

**Why a stale snapshot can't stay stale.** In the race, A and B upload snapshots that each lack the other's change, and B's, the later one, wins. A's base version is now behind the server's, so its next manifest sync looks at the item. If A's doc already holds B's heads, it has other heads too and uploads; if not, it fetches B's snapshot, merges it, finds local changes and uploads. Every other device that pulled A's change holds an unconfirmed pull, so if A never comes back, one of them uploads once the grace period is over. Uploads, rewrites and changes too large for a row all heal this way.

So the server's snapshot can lack a change for up to an hour (A's next manifest sync), or a day if A never returns. Only a device that hydrates from a snapshot without reading the log is affected: a new or long-away device reads the whole retained log after catch-up's manifest sync, and the log keeps rows for 30 days. `replaceFromServer` in that window gets the change at a later manifest sync. If A never returns and every device that pulled the change stops syncing within the day, the log row is its only copy on the server, and it goes when the row expires.

An earlier rule had the later writer recheck once its log cursor reached the head at its write and upload again. It healed within a poll but needed a store, a log-head read on every snapshot upload and a step on every pulled page, so it was removed: S2 heals the same race.

**Rewrites.** `SnapshotRewriter` rewrites every item's snapshot (for a key rotation, or once per device for the bound snapshot format), and it's a phase of the poll: a request queues every item and asks for a poll (`orchestrator.pollNow`), and `SyncPoller.executePoll` runs `SnapshotRewriter.runDue` after the snapshot phase. So rewrites share the poll's leadership, online state, abort, auth pause and backoff, and record what the server stored through the same `SnapshotPusher.recordStoredSnapshots`. The phase skips the poll until the device has caught up (`SyncLogPuller.isCaughtUp`), as the snapshot phase does: a device that hasn't read the log within its TTL, or has reset its sync state, merges the server's snapshots in catch-up's manifest sync first, or a rewrite could replace a snapshot holding what its doc lacks. It drains the whole queue within the poll, a chunk at a time. Each chunk is pushed before it's built, and `buildAfterPush` pushes and builds again an item whose doc changed since (S1). An item that isn't built or stored goes back on the queue, up to `MAX_REWRITE_ATTEMPTS`. After that it goes in `failed`: quarantined if its build or upload failed, and not if it was still waiting for the log, so a later rewrite can retry it. A request that fails (network, server, auth, a refused build) fails the poll (rule 4) and keeps the rest of the queue for the next poll, so a rewrite resumes where it stopped.

A request waits first, as the poll would, for this tab to lead (claiming the leadership) and for catch-up. Every wait is bounded for a caller that asks: with `waitTimeoutMs`, either wait gives up with a `ReencryptionWaitError` naming the stage, having changed nothing. `prepare` waits the same way without queueing anything, so the key rotation coordinator (`reencryptAllItems` in `keys/reencrypt.ts`) can stop before it rotates the key on a device that can't push. A request made during a pass starts it again over every item (the key may have rotated since), and every caller gets the new pass's result. A poll that stops or fails, in any phase, rejects the callers waiting (`onPollStopped`) rather than leaving them to wait out the backoff, and so does a request when no poll can run. A caller's signal only stops that caller waiting, and `cancel` clears the queue and stops a pass in flight. The rewrite reports its stage (`waitingForLeader`, `waitingForSync`, `reencrypting`) as `reencryptStage` events, and `getSyncDiagnostics` reports it with the leadership and whether the device has caught up.

## Moving onto the log

The log started empty at the cut, and nothing was copied from the table it replaced: snapshots carry the data across, and each device uploads what it has that they lack. Old server heads can't be trusted, because they can name changes only the old table held.

A device that synced before the log resets its sync state for it once per account (`resetSyncState`), and the engine then treats it as it treats any device with no server heads. The reset runs only in the migration app. Its finish is device level 4 (`syncResetDataVersion`), and the main app's device gate (`MIN_DEVICE_DATA_VERSION` 4) sends any device with local data below it there first. A session whose `minDataVersion` is at or above `syncResetDataVersion` doesn't run it. A new device starts at the current level and needs no reset, because it has no old server heads.

- **The reset.** Inside the `withLocalDataLock` call that opens local storage, it marks every active item pending, clears the old server heads (from each item's sync record) and the old cursors, and persists `firstStartReset`. The flag comes last, so an interrupted run repeats, and it never runs again, because a later tab would otherwise clear heads the leader has set. A device that ran first start's local part has the flag already, and its items are pending with no server heads, which is all the reset does. Nothing local is reset (rule 10).
- **What the engine does next.** With no log cursor, the first poll runs catch-up's manifest sync before anything is pushed (`SyncLogPuller.demandCatchUpIfBehind`, then the `beforeRead` manifest phase). That merges every snapshot newer than the item's base version, and a merged snapshot's heads become the item's server heads (`onItemSnapshotHydrated`), since it has none, so the push sends only what the snapshot lacks. An item whose snapshot isn't fetched (its base version has already reached the server's) has no server heads, so its push sends its whole history. Receivers ignore changes they already have. S1 holds back each snapshot until its push has landed.
- **No uploads before catch-up.** `SnapshotPusher.pushDue` uploads nothing until the puller has caught up (`SyncLogPuller.isCaughtUp`). Catch-up's manifest sync uploads the dirty items before it fetches the manifest, and a device that has reset (or been away longer than the TTL) could otherwise replace a snapshot holding what its doc hasn't merged yet. Rewrites wait for the same thing (see "Rewrites").
- **Finishing.** The device has finished once the reset has run and the WAL is gone: `hasFinishedSyncReset` clears any leftover WAL with `clearWriteAheadLog` and persists `walCleared`, trying again at the next check if that fails. `DataVersionTracker` caps the device level at 3 until then, and records the level only after a sync without failures.
- **Cost.** A large straggler pushes about its whole size to the log, within the log quota (see "Server limits"), with 429 backoff in between.
- **A merge that fails.** If catch-up fetches the manifest but an item's snapshot can't be fetched or hydrated, the device is still caught up, so it can upload a snapshot that lacks what the one it replaced held. Uploads are last-write-wins, and S2 heals it at the next manifest sync of any device that holds those changes. First start held such an item back (`awaitingHeads`) until it had resolved; the reset doesn't.

- **The WAL wasn't migrated.** Nothing replays it, because each device's doc nearly always holds the same changes. A change that only reached the WAL (a tab killed straight after an edit, or a doc save that failed on full storage) was dropped at the cut: the one accepted exception to never resetting local data without the user confirming.
- **Why a device level gates it.** A device that skipped the reset would trust old server heads. A protocol version can't tell that, because it gates builds, not a device's data (`MIN_PROTOCOL_VERSION` 5 already requires the log). The device level can, the way level 3 waits for sealing. The engine has no path of its own for the reset beyond the reset itself and the level cap: everything after it is what any device does.
- **First start.** Before the reset, the migration app ran first start, which kept a record per item until it had resolved its server heads from the manifest, so that no item pushed its whole history. It was retired from the engine because it added ten branch points to code the main app runs on every poll, which never took them. Its `first-start` store and `firstStartSynced` key stay unused, because names never change.

## Snapshot sync

- **Uploads are a phase of the poll.** `SyncPoller.executePoll` ends with `SnapshotPusher.pushDue`, after the push and pull, and then the rewrite phase (see "Rewrites"), so snapshot uploads share the poll's leadership, online state, abort, auth pause and backoff: there is one outbound loop and one backoff per outage. An expired session pauses uploads with polling rather than leaving them to retry on their own. The push before the build makes S1 hold by construction in the common case, and the synchronous check stays as the guard for an edit in between.
- **When uploads are due.** `SnapshotSchedule` keeps the dirty items (see "Dirty items") and a due time: 15 min after the last edit (`snapshotDebounce`), at most 1 h after the first (`snapshotMaxWait`), or sooner for a request with its own delay (`requestSnapshot`, `upstreamSnapshotDebounce`, `restoredSnapshotDelay`), which later edits don't put off. The orchestrator schedules the next poll at the earlier of its cadence and the due time (`getSnapshotDueAt`), and `onSnapshotDue` brings a scheduled poll forward when an edit makes snapshots due sooner. Neither overrides failure backoff or an auth pause.
- **Why uploads are lazy.** A snapshot rewrites the whole item, so it's the most expensive write (about one WCU per KB), while the log already delivers each change to other devices for 30 days. The cadence only has to stay well under `pulledChangesGrace` (1 day), or pulling devices upload duplicates under S2, which is harmless but wasteful. Hiding the page (`onPageHidden`) saves the item records and flushes the log push, but doesn't make snapshots due.
- **Dirty items.** Within a session the dirty items are counted with ticks, so an edit made while an upload is in flight keeps the item dirty: a confirmed upload clears an item only if its tick hasn't moved. Across sessions, each item's sync record carries a `dirty` flag. It has one writer, the leader: it sets it as it records a push's acknowledgement, in the same save as the item's server heads, and for the snapshots it asks for itself (`requestSnapshot`, S2, restores on the leader); it clears it when the item stops being dirty (saved after a 1s debounce, at most 5s, and at once when the page is hidden); and the startup and promotion audit re-queues every flagged item that isn't quarantined, due after `restoredSnapshotDelay` (1 min) rather than a fresh debounce: a device whose sessions all end before the debounce (a phone app opened briefly each day) would otherwise never upload them, and once the log rows expire a device hydrating from snapshots would miss those changes. An edit made after an item's push is acknowledged gets a new mark, and its own acknowledgement makes the item dirty again, so the snapshot that follows holds it. No clock is involved.
- **A follower's edits.** A follower only writes the pending mark, which every tab shares, so the leader pushes the edit and its acknowledgement queues the snapshot; nothing is sent between tabs. The mark usually lands before the follower's change reaches the leader's doc, so when the leader finds unpushed changes on an item that is already marked (`ChangeOutbox.onDocChanged`), it still queues a poll, rather than leaving the edit for the next cadence.
- **Mixed releases.** A tab of an earlier release still sends `item_dirty` messages, which this release ignores, and doesn't mark items dirty on acknowledgement. Under such a leader, a new follower's edit reaches the log but this device never uploads its snapshot; S2 uploads it after `pulledChangesGrace`. That's accepted, and nothing needs deleting once old tabs are gone.
- **Failures.** An item that fails (not ready, deferred, rejected by the server) stays dirty and goes up at the next poll, which doesn't bring a poll forward, so a failing upload can't loop polls. After `MAX_CONSECUTIVE_SNAPSHOT_FAILURES` (5, `SnapshotPusher`), the item is quarantined and dropped from the dirty queue. A request that fails fails the poll.
- **Flushing.** `flushPendingSnapshots` (recovery actions, the storage quota dialog, counting unsynced changes) makes every dirty item due now and runs a poll (`SyncOrchestrator.pollNow`), after the one in flight. It runs one when items have pending marks but none is dirty yet too: the poll pushes them first, and their acknowledgement makes them dirty, due in the same poll's snapshot phase. A manifest sync uploads first so the manifest includes those items: it makes every dirty item due now and calls `pushDue` itself. It's a phase of the same poll, so the two uploads never run at once.
- **The sync indicator counts pending marks only** (`countUnpushedChanges`). A dirty item's changes are already in the log, so showing it would report edits as waiting for the whole debounce. `getUnsyncedChanges`, for removing an account or exporting a backup, counts dirty items too: a device that hydrates after the TTL has only snapshots to go on. It counts pending marks together with the stored dirty flags, reloading the records first (a load keeps this tab's unsaved values), so a follower counts what the leader has pushed but not uploaded.
- **Stuck items.** Marks older than `stuckPendingAge` (a day) are reported as `stuckItems` by reason: the mark's `blocked`, else `unknown`. The indicator shows them as delayed, with what holds each up, rather than as syncing shortly.
- **Poll cadence follows visibility and activity.** The leader polls at one of three rates, which `SyncOrchestrator` picks each time it schedules a poll:
  - **Active (10–15s).** A tab is visible and there was activity in the last `activityWindow` (2 min). Activity is input in any of the account's tabs (`SyncDOMListeners` reports it at most every 5s, and the tab-visibility message carries it to the other tabs), or a pull that applied changes from another device.
  - **Idle (30s).** A tab is visible but nothing happened lately.
  - **Hidden (5–10 min).** None of the account's tabs on the device is visible.

  The active and hidden delays are drawn afresh at random from their ranges, which is their jitter. When activity starts while the next poll is more than 15s away, `onActivity` brings it forward. Failure backoff overrides all three, and local edits still flush at once. When the user comes back to a tab (it becomes visible or gets focus), `SyncOrchestrator.onForeground` polls now and resets backoff, unless a poll is running or one finished in the last `foregroundPollMinGap` (10s). There's no server push: Web Push would show a notification for every nudge.

### Monotonic versions (no clock-based reconciliation)

`putSnapshots` runs an atomic `version = if_not_exists(version, 0) + 1` and returns the new version. The client stores it as `baseVersion` in the item's sync record. `calculateSyncDeltas` then decides:

| Condition | Action |
|---|---|
| V_server > V_base | Fetch the snapshot and merge it into the local doc |
| V_server > V_base and server deleted | Apply the tombstone locally |
| V_server ≤ V_base and dirty | Push a snapshot |
| V_server ≤ V_base and clean | Do nothing |
| Item missing from the server manifest | It was created offline, so push a snapshot |
| Quarantined, V_server ≤ max(V_failed, V_base) | Skip (unless forced) |
| Quarantined, V_server > max(V_failed, V_base) | Fetch the snapshot to retry recovery |

No decision in this table compares clocks, and nothing else in sync does: dirtiness is a flag (see "Dirty items"), and a quarantine is compared by version. "Locally tombstoned" means the index's `tombstoneIds`, which every removal from the index adds to (`AutomergeIndexManager.removeItemIds`). An item this device knows only by its base version, neither indexed nor tombstoned, counts as unknown, so a live server copy is fetched: hydration merges into any local doc (rule 2), a merged doc that's deleted is tombstoned rather than indexed, and one that isn't is indexed again. A deleted manifest entry is never fetched, so a server deletion of an item this device never had only records its version.

V_base advances only when this device pushes or hydrates a snapshot, not when the log delivers the same changes. So every item edited on another device looks stale, whether or not this device missed anything. **Heads in the manifest** keep that cheap:

- Each snapshot upload carries `heads`, the Automerge heads of the saved doc, encrypted with purpose `heads` (see "Doc-bound ciphertexts"). The server stores them with the snapshot and returns them in the manifest.
- Before computing deltas, `findSnapshotsCoveredLocally` decrypts the heads of each active, non-quarantined item with V_server > V_base and checks `Automerge.hasHeads` against the local doc. If the doc already has them, `ManifestSyncManager` raises V_base to V_server, and the table above then treats the item as up to date. A dirty item is still pushed, and a doc that holds more than the snapshot gets a new one (S2 in "Snapshot coverage").
- Anything that can't be checked (no heads, a missing key, a doc that isn't loaded, heads that fail to decrypt) is fetched as before. A heads failure never quarantines an item. Forced syncs skip the check.
- **Every write sets or removes `heads`** (`updateItemCommand`). Heads left from an older snapshot, paired with a newer version, would make clients skip a snapshot they need. A write without heads (older builds, tombstones, legacy writes) removes them, and the manifest leaves them out for deleted items.

An item whose hydration throws (not a decryption failure, a missing key or a legacy row without a hook) at `REPEATED_ERROR_LIMIT` (3) manifest syncs in a row this session is quarantined as `unknown` with the version that failed. Otherwise it would fail every sync, no sync would count as complete, and the device level (`DataVersionTracker`) would never be recorded.

A quarantined item's manual recovery entry records `serverVersion`, the server version that failed (for example a snapshot that couldn't be decrypted), as V_failed. A failed hydration doesn't advance V_base, so without it the same broken snapshot would be fetched and fail again on every manifest sync. Entries without `serverVersion` (stored before it existed, or quarantines not tied to a server version) fall back to V_base. The comparison never uses the entry's `createdAt`, which comes from this device's clock.

### Snapshot writes are intentionally LWW (no OCC)

`itemsRouter.putSnapshots` overwrites without a version condition. This is safe for four reasons:
- Snapshots are recovery baselines, and overwriting one never touches any client's local doc.
- Every edit reaches the log before any snapshot holds it (S1), and S2 catches up a snapshot that replaced another device's.
- Hydration merges rather than replaces (`existingHandle.merge(...)` / `Automerge.merge`). A stale snapshot cannot clobber newer edits, because merge(A+B, A) = A+B.
- When a client merges a stale snapshot, `hydrationResult.hasLocalChanges` is true, so it calls `markItemDirty` and re-uploads the merged state.

OCC would be harmful. A blind relay cannot resolve conflicts, so concurrent or offline flushes would churn on retries and eventually false-quarantine healthy items. OCC is reserved for centralized, non-CRDT state such as `keyringVersion` during key rotation.

## Deletion and IDs

- Deletes are soft-deletes. The CRDT doc gets `deleted: true`, and that propagates through messages and snapshots (`metadata.deleted`). `FlockItems` rows are never hard-deleted and have no TTL.
- The server never clears `metadata.deleted`. A later snapshot from a device that hasn't seen the delete yet still bumps the version but keeps the item deleted.
- **Deleted content.** Every tombstone write, including that late snapshot, removes the row's `snapshot`, legacy `cipher` and `heads`, keeping only `metadata`, `version` and `modifiedAt`, so the manifest is unchanged. Nothing reads a deleted item's content: manifest sync records a deleted entry without fetching it, and hydration returns early on `metadata.deleted`. The item's log rows go with the log's 30-day TTL. Rows deleted before this kept their snapshot until the `dropDeletedItemPayloads` migration.
- A hard-delete would be undone. An item missing from the manifest looks like an offline creation, so manifest sync would re-upload it. Deleting the whole account is the one exception (see below).
- Deletion is terminal, with no undelete. New items always get a fresh `generateItemId()` (126-bit nanoid). Reusing an ID would merge the old entity's history into the new one.
- `AutomergeDocStore.findOrCreateHandle` refuses to create a blank doc when `hasDataInStorage(itemId)`. This guard prevents data loss: without it, a handle-lookup timeout would overwrite an existing doc.
- Selectors filter `!item.deleted`, and `AutomergeIndexManager` excludes tombstones from the active index.

### Account deletion

Deleting an account (Settings → Delete account) hard-deletes everything the server holds for it, in this order, each step retryable:

1. The client checks the password against its unlocked keys (`confirmAccountPassword`), so a wrong one never reaches the server as an UNAUTHORIZED the app would take for an expired session. It then stops sync on this device without clearing local data, so nothing is pushed after the server's copy goes.
2. `accounts.deleteItems`, called until it reports `done`, first sets `deletingSince` on the account record, which makes every login fail, and ends every session but the caller's and forgets the login devices. Without that, another device would silently log in again with its in-memory key hash and re-upload the missing items. It then deletes a bounded round of `FlockItems` rows and, once they're gone, of `FlockSyncLog` rows (head row included), so each request stays within the Lambda's timeout.
3. `accounts.deleteAccount` deletes the account record, which also drops its push subscriptions and its `ReminderIndex` entry. Every other account write is conditional on the record existing, so nothing recreates it.
4. The client removes the account from this device exactly as "Sign out & remove local data" does (`removeVaultFromDevice`).

Both server procedures need the password-derived auth token as well as the session. If the user carries on past a failed step, what's left is ciphertext on an account that can no longer log in.

## Concurrent string edits

Item writes are diffs: `applyItemUpdatesToDraft` skips unchanged fields, so a whole-item save doesn't overwrite remote edits to fields it didn't change. Changed strings are handled in one of two ways:

- **Merged text.** Keys listed in `SyncDomain.mergedTextFields` go through `Automerge.updateText`, so concurrent edits merge character by character. This suits long free text, where keeping both edits matters more than a clean result. Edits to the same spot can interleave, and identical edits duplicate.
- **Everything else is replaced whole.** One concurrent edit wins, chosen by Automerge's op ordering rather than by time, so every device agrees but the older edit can win. Merging characters here would garble names, and would turn enums into invalid values: two devices both setting `all` would merge to `allall`, which fails validation.

New string fields are replaced whole unless the app lists them. A field that moves between the two needs no migration, because assignment and `updateText` both work on either kind of value.

## Account settings document

Account settings the app syncs (`SyncDomain.syncedMetadataKeys`) live in an encrypted Automerge document managed by `AccountSettings`. Other metadata keys stay in the device's local index. The worker merges both and emits them as `metadataUpdated`, with the document's values winning.

- **Fixed ID.** The ID is `settingsDocId(account)` (`settings-${account}`), so every device agrees on it without coordinating. This is the one exception to "never recreate a doc under an existing ID": two devices can create it concurrently, for example while migrating. Their histories merge because each setting is a top-level key. Two devices that first create the same nested object concurrently keep only one of them, so prefer flat values.
- **Created lazily, never deleted.** The document is created on the first write of a synced key and never seeded with defaults, which would overwrite real values from other devices. `forceDeleteRecoveryItem` and `recreateOversizedItem` refuse it.
- **Writes are diffs.** The app sends whole objects, so `AccountSettings` skips unchanged keys and edits nested maps and lists in place. Replacing a map would discard a concurrent edit to another field.
- **An ordinary document otherwise.** It is in the item index, so the log, snapshots, manifest sync, key rotation and backups all handle it. The worker filters it out of the `indexUpdated` event sent to the app (`SyncWorkerContextConfig.onIndexUpdated` still sees it, so the worker subscribes to it) and routes its changes to `AccountSettings` instead of `itemUpdated`. `withSettingsDocPassthrough` keeps it away from the app's codec.
- **Legacy migration.** After each manifest sync, so that the server's copy has been hydrated first, `migrateLegacySettings` copies settings from the app's `LegacySettingsSource` and from local metadata into the keys the document lacks, clears the source and then strips the local keys. Keys already in the document win, because another device migrated them first. A failure leaves everything in place for the next sync. Failures are logged and never fail the manifest sync.

## Doc-bound ciphertexts

Snapshots and log rows are encrypted with `vault-doc:<itemId>` as AES-GCM associated data and marked `format: 2`. Snapshot heads use `vault-heads:<itemId>` (purpose `heads`), so heads can't be served as a snapshot or the other way round (`DOC_BOUND_FORMAT` in `packages/vault-shared/src/crypto.ts`). Without it, the server could serve item A's snapshot as item B's, and B's device would merge A's whole history into B, which cannot be undone.

- **Bind the ID the plaintext is applied to.** `snapshotBuilder` and `ChangeOutbox` encrypt with the item ID; `ManifestHydrator`, `SyncLogPuller` and `GapHealer` decrypt with the ID of the doc they apply the result to. Taking the ID from a separate field in the server's response would defeat the check.
- **The flag cannot be used to downgrade.** Stripping `format` from a bound ciphertext makes it decrypt without associated data, which fails. An unknown `format` is rejected.
- **Unbound ciphertexts still decrypt for now**, because older snapshots are unbound. Until they are rejected, a malicious server can still serve unbound ciphertexts it kept. `SnapshotFormatUpgrade` rewrites every snapshot once per device after a manifest sync without failures (or one skipped because a clean sync ran within `manifestSyncMinGap`), when local docs include everything in the server's snapshots. It runs only in the leader tab and at most once per session, so a persistently failing item doesn't re-upload everything on every sync.
- **Every server path must keep `format`.** zod strips unknown keys and the Dynamo driver copies snapshot fields by name, so a field missed anywhere silently makes bound ciphertexts undecryptable.
- **Not bound:** the keyring, cross-tab BroadcastChannel messages and backup files. The server holds only one keyring per account and never sees the other two. Binding also does not stop the server replaying an older snapshot of the same item; hydration merges, so that only matters to a device that has never seen the newer state.

## Oversized items (ID rotation, never in-place compaction)

Snapshots are limited to 350 KB. A fresh `Automerge.init()` doc under the same `documentId` would have disjoint heads. Any peer or snapshot carrying the old history would then merge back in and resurrect it. So `ItemOperations.recreateOversizedItem` works like this:
1. It rejects the request if the item's current content (without history) is over 300 KB, because the user has to reduce it manually.
2. It creates and indexes a new doc under a new random ID with the latest content, then remaps group memberships from the old ID to the new one.
3. Only then does it soft-delete the old item. If any step fails it throws, which leaves the old item indexed and quarantined, so a retry is safe. Concurrent calls for the same ID are merged with a `KeyedSingleFlightGuard`. If the source item is already deleted, it finalises the previous recreation (index removal, unquarantine) and does not create another copy.

The deleted old doc still exceeds the limit. `SnapshotPusher` therefore uploads a payload-less tombstone (`toTombstoneSnapshot`: `deleted: true`, no `snapshot`) and does not quarantine it. The server sets `metadata.deleted`, bumps the version and removes the stored snapshot, legacy `cipher` and heads, as it does for every tombstone (see "Deleted content" under "Deletion and IDs"). It only does that to an item it already has (`attribute_exists(item)`): for an ID it has never seen, which happens when the oversized item never reached it, it writes nothing and answers with version 0, so the push succeeds without a row. Rows for unseen IDs would get round the storage quota and grow the manifest for good, since rows are never removed. Such an item is missing from the manifest, so each manifest sync pushes its tombstone again, a request that writes nothing. Hydration returns early on `metadata.deleted`, and no synced heads are recorded for tombstones.

## Manual recovery store

Items that can't be synced are quarantined in `manualRecoveryStore` and shown to the user.
- `kind` is one of `pullDecryption`, `snapshotDecryption`, `oversized`, `snapshotFailure`, `localDecryption`, `missingChanges` or `unknown`. For legacy entries it is inferred from the reason text. Entries from before `pushFailure` was removed read as `unknown`.
- `detail` says why, as a `ManualRecoveryDetail`: a fixed code plus at most a size or a stage. The store is unsealed, and an error message can quote decrypted content, so `quarantine` takes no error and callers log it instead. The displayed `reason` is built from `detail` when the entry is read. Reading rewrites entries from older builds, which stored a free-text reason, without it.
- `pullDecryption` is auto-cleared only by a successfully applied entry from another device. Own push echoes are excluded via `SyncLogPuller.recordOwnPushes`. The `GapHealer` clears `missingChanges` when it heals the item.
- A server-confirmed snapshot upload clears every kind, as does any explicit user action (retry, overwrite, delete, recreate, dismiss).
- `serverVersion` (optional) is the server version that failed; manifest sync skips the item until the server has a newer one (see "Monotonic versions"). An upsert keeps the highest version seen, even when a weaker kind doesn't replace the entry.
- A weaker quarantine never overwrites an `oversized` entry. Oversized detection (`SnapshotSchedule`, `DataRecoveryDialog`) checks `kind`, never reason text.

## Multi-tab and leader election

- `LeaderElection` uses `navigator.locks`: the leader is the tab that holds the account's leader lock, and every other tab queues for it. **Only the leader talks to the server:** polls, pushes, snapshot uploads, manifest syncs and snapshot fetches (`ManifestSyncManager` does nothing in any other tab). Followers keep a live Repo and get the leader's docs through shared storage and `EncryptedBroadcastChannelNetworkAdapter`, so sync state (server heads, base versions, dirty items) has one writer.
- **Session start.** `bootstrapItems` runs a manifest sync only in the leader, through a poll (`SyncOrchestrator.syncManifest`). A device with no items that couldn't fetch the manifest fails startup so it's retried, unless the session has expired. A tab whose lock request is still pending while no other tab holds the lock waits up to `leadershipSettle` (5s) to learn it leads (`SyncOrchestrator.settleLeadership`), so a new device's first tab still loads its items before startup finishes. A tab that only learns later syncs when it's promoted.
- **Taking over is a lock steal.** `claimLeadership` requests the lock with `steal: true`, which the browser grants at once, rejecting the holder's request with an `AbortError`. The holder treats that as losing leadership and queues again. Leadership is only ever held with the lock; the one exception is a browser without Web Locks, or whose lock requests keep failing, where the tab leads without it.
- **User actions that need the server** (`fullResync`, `replaceFromServer`, re-encryption) steal leadership first (`SyncWorkerContext.becomeLeader`, which waits for the grant). `replaceFromServer` takes over before it drops the local copy. A forced sync waits for a sync in flight rather than sharing it, since that one may not be forced.
- **Leadership follows the visible tab.** A follower the user comes back to steals leadership if no visible tab leads (`ForegroundTracker.onLeaderAway` → `SyncOrchestrator.followVisibleTab`). Switching tabs, the old tab's report that it's hidden can arrive after the new one returns, so a leader that reports it's hidden within `leaderHandoffWindow` (2s) of the return counts too. A tab steals this way at most once every `leaderHandoffMinGap` (10s), so tabs can't thrash. This is also what unblocks a **frozen leader**: a browser that freezes a background tab doesn't release its Web Lock, so until the user comes back to another tab, that tab gets nothing from the server (it still has everything the device had, in shared storage). The frozen tab learns it lost the lock when it thaws.
- **Two tabs may lead at once** between a steal and the old leader handling its rejected request. Nothing relies on there being one: pushes resend changes Automerge ignores as duplicates, snapshots merge, and server heads are saved per item. Broadcast sync between the tabs carries on throughout.
- **Tabs of the previous release** ignore a stolen lock but yield to a `claim` on the presence channel, so the leader sends one when it starts leading and every 2s after, and `release` when it stops (`LegacyLeaderClaims`). Delete it, and the `leaderPresenceChannel` name, once no tab of a release before lock stealing can be open.
- Every tab runs a `ForegroundTracker`, which sends `tab_visibility` messages on the `RealtimeBus` sync channel when its visibility or leadership changes, every 30s while it's visible, and in answer to a tab it hadn't heard from, so a hidden leader keeps the foreground cadence for a visible follower. Each message says whether the tab leads. A tab that stops pinging counts as hidden after 75s. A follower the user comes back to sends `returned`, and the leader polls for it.

### Missing key version on cross-tab messages (intentional inline wait)

When a message arrives with a `kver` that is not in the keyring, the receive queue `await`s `waitForKeyVersion(kver, timeout)` and fires `onKeyVersionMissing`. This is not a head-of-line blocking bug, for five reasons:
- It only happens during key rotation or a password change.
- The key normally arrives via `localStorage` / `VAULT_EVENTS_CHANNEL` within about 10–50ms.
- Waiting preserves causal ordering.
- The following messages from that tab need the same key anyway.
- After `keyWaitTimeoutMs` (5s), the message moves to `pendingKeyMessages`, `waitForKeyAndDrain` takes over in the background, and the queue resumes. No messages are dropped.

Cross-tab sync is an ephemeral optimisation. IndexedDB and the server remain the durable source of truth.

## Local storage layout

- Automerge docs: `VaultIndexedDBStorageAdapter`.
- Sync log database (`syncLogDatabase` + account), which `SyncLogDatabase` opens directly rather than through localforage: pending marks, parked entries, the unused `first-start` store and each item's sync record (`items`: server heads, base version, dirty flag, `snapshotOnly` and `pulledAt`). None of it needs a seal: it holds IDs, heads and counters, and parked entries hold the server's ciphertext. Each record is per item, so a write is one transaction (`update`) that touches only the items it changes, and tabs never race on a shared value. Version 2 of the database added `items`, and version 3 deleted `snapshot-rechecks`. The upgrade adds stores that are missing and deletes removed ones; every device reaches version 3 in the migration app, so the deletion can go when device level 4 is retired.
- **Item sync records** (`ItemSyncState`) are the one model of what the device knows about each item's server copy. Every tab holds a copy, loaded once at start and once on promotion (with the log state, which the first poll waits for), and saved by one debounced save (1s, at most 5s, and at once when the page is hidden). Tabs don't all know the same: only the leader writes dirty flags, server heads, `snapshotOnly`, pulls and uploads (followers read the records, to count what's unsynced), and a tab that has just stopped leading can still save after the new leader loaded. So changes are tracked per item and per field, and a save writes only the fields this tab changed, keeping the stored values of the rest; a load keeps this tab's unsaved values over the stored ones. Base versions only rise, in memory and against the stored value on save (rule 8). Only the leader clears a dirty flag: an upload, an oversized quarantine or a manifest delete. `SnapshotSchedule` holds what's only for the session: the queue's ticks, due times, retry and quota deferral, and the items known to be oversized.
- **The `unconfirmed-pulls` store** held S2's records before they moved into `pulledAt`. For one release, `ItemSyncState.load` folds its entries into the records (keeping the earlier time) and deletes them once they're saved; the store can be dropped after that, without a database version change.
- A WAL left by an older build, in its own databases, until the migration app clears it (`hasFinishedSyncReset`). Nothing reads it.
- Sync metadata: one database per account, `flock-sync-metadata-${accountId}` in Flock (store `sync-metadata`), opened once via `getSyncMetadataStorage(accountId)`. Its keys are `logCursor`, `logLastPullAt`, `indexDoc` or `indexDocSealed`, `snapshotsDocBound`, `deviceDataVersion`, `lastSyncedAt`, `firstStartReset` and `walCleared` (and `firstStartSynced`, which nothing reads now). The stores only read the current layout. Until level 4, `lastModified` (each item's timestamps and base version) and `syncedHeads` held every item in one value; the migration app moves them into the item records (see "Level 4" in [vault-extraction.md](vault-extraction.md)).
- Sealed storage (`upgradeLocalEncryption`, Part 2 of [local-encryption.md](local-encryption.md)): user content is sealed with a per-device storage key (DSK), wrapped with a data key and kept in the sealed Automerge database's `meta` store (`dsk`, plus `upgradedAt`).
  - **What's sealed:** Automerge chunks go to the sealed Automerge database (`sealedAutomergeDatabase`) as `{ key, v, iv, ct }`. The index is sealed under `indexDocSealed`.
  - **What stays readable:** storage keys, the sync log database and the other metadata keys hold no user content.
  - **Associated data:** each record is bound to its account, store and position, so a record moved anywhere else fails to open.
  - **`openLocalStorage`** picks sealed or plaintext storage under the `localDataMigrationLock`, after the `migrateLocalData` hook and before the Repo exists. It copies any plaintext data across and retires the plaintext stores once no other engine holds the account's sync locks.
  - **Decrypt failures:** a record that fails to decrypt is never treated as missing. The document is quarantined as `localDecryption`, and if the DSK itself can't be opened, sync stops and the app is asked (`onLocalDataUnavailable`). Nothing is ever reset automatically.
- Older layouts: the worker config's `migrateLocalData(accountId)` hook runs at the start of `SyncWorkerContext.initialize()`, before any store is read, under the `localDataMigrationLock` Web Lock so tabs take turns. A failure fails initialization, because starting would create an empty index that a later migration would keep over the old one. Flock passes this hook only in its migration app (`src/migrate/legacy/localData.ts`). It imports Flock's per-store databases, the consolidated store's earlier keys and old value shapes, and deduplicates manual recovery entries (its own `manualRecoveryMigrated` key).
- Data levels: with `minDataVersion` set, `initialize()` first checks `deviceDataVersion`. Below the minimum, a device with an index, or with data the app's `hasLegacyLocalData` hook finds, doesn't start: the worker emits `migrationRequired` instead. This check has to come first, because starting records the current level for a device with no index. Likewise, a server row without a snapshot, when the app has no `decodeLegacyItem` hook, is skipped rather than quarantined and reported as `migrationRequired` (see "Backwards compatibility" in [vault-extraction.md](vault-extraction.md)).
- All storage names come from `VaultStorageNames` (`packages/vault-client/src/shared/storageNames.ts`). Renaming one orphans the data stored under the old name.
- Logout or reset: `clearAccountLocalData` → `clearSyncMetadataStorage` drops the whole metadata database. The store-level `.clear()` only clears its own key.

## Shutdown order (`ServiceLifecycleManager`)

- Each session's components share one `SyncSessionState` (online, leader, shut down) and take the account in their constructor; a new account gets a new context. `SyncWorkerContext.shutdown` marks the session shut down first, so no component starts new work, then the lifecycle stops each component exactly once, in reverse registration order. Nothing else stops a component: a second stop with other options (such as without `clearLocalData`) could save state during a data clear.
- The context's `RealtimeBus` (cross-tab sync pings, tab visibility, index and metadata messages; edits need none) is registered first, so it closes last.
- Shut down the Automerge Repo before clearing IndexedDB. Otherwise pending saves write data back into the cleared database.
- Don't run `clearSyncMetadataStorage` (`dropInstance`) concurrently with per-store `.clear()` calls on the same database.
- The sync log database closes after everything that writes to it, because an open connection blocks `deleteDatabase`. Its connection also closes itself on `versionchange`.

## Event hub concurrency

`ClientEventHub.emit` is fire-and-forget. Async listeners are not awaited, and their rejections are caught and logged. This keeps producers such as item updates and request tracking from being slowed by listener I/O. Listeners must therefore handle concurrent in-flight invocations themselves, using `SingleFlightGuard`/`KeyedSingleFlightGuard`, `AsyncMutex`/`KeyedAsyncMutex`, `ItemLockCoordinator`, `AsyncQueue` or monotonic tick counters (for example `SnapshotSchedule.dirtyItemsTick`).

Inside the worker, components call each other through plain callbacks that `SyncWorkerContext` wires up. A callback that starts async work runs it with `fireAndForget`, so the same applies to it: pushes, pull processing and Repo network events aren't slowed by it, and it must synchronize itself.

## Server limits

- `appendLog` writes at most 99 rows and about 3.5 MB per transaction, under the `TransactWriteItems` limits, and retries with jitter on a conflict. `ChangeOutbox` sends requests within `logPushRows` and `logPushChars`.
- Each pushed log row's `cipher` is capped at `MAX_LOG_CIPHER_LENGTH`, a full `MAX_INCREMENTAL_MESSAGE_BYTES` row once encrypted and base64-encoded, so a longer one is refused with `BAD_REQUEST` (which `ChangeOutbox` treats as a refused row) instead of failing in DynamoDB as a 500.
- `fetchSnapshotsByIds` chunks reads into groups of 100, the `BatchGetItem` limit. A client sends `maxResponseChars` (`MAX_FETCH_RESPONSE_CHARS`, 4 MiB), because 50 items of up to 350 KB can pass Lambda's 6 MB response limit; the server returns items until the next would pass it, always at least one, and lists the rest in `deferred`, which `ManifestHydrator` asks for next. A request that defers everything fails the sync rather than repeating forever. Requests without the field get every item, as before.
- `UnprocessedKeys` are retried with jittered exponential backoff.
- **Per-account quotas** (`AccountQuotas` in `packages/vault-server/src/quotas.ts`, overridable through `VaultServerOptions.quotas`) bound what one account can cost. Real accounts are far below them. A request past one gets `TOO_MANY_REQUESTS` with `QUOTA_EXCEEDED_MESSAGE`, which the client classifies like any 429: the poll fails, backs off and retries later, and the changes wait in the local doc. A refused snapshot upload defers snapshots instead of failing the poll (see "Poll result contract"). Neither quota rejects single items, which would make `pushItems` and `SnapshotPusher` quarantine items that are fine.
  - **Log bytes per UTC day.** The head row keeps `usageDay` and `usageBytes`, rewritten by every append in the same transaction, so the head condition that orders appends also keeps the count exact. A push that would pass the quota appends nothing (for a push spanning several transactions, nothing from that one on). Rows expire after `SYNC_LOG_TTL_DAYS`, so this also bounds the log an account holds.
  - **Stored item bytes.** The account record keeps `storageBytes`. Each item write returns its record as it was (`ReturnValues: 'ALL_OLD'`, which costs no read capacity), which gives both the new version and how much the write grew the item, and `putSnapshots` adds the batch's total with one `ADD`. That isn't in a transaction with the writes, so a failure in between leaves the count low; `recountStorageUsage` recounts from the items. A batch that carries any snapshot is turned away whole once the account is at its quota, checked against the usage when the request came in, so an account can pass it by about one batch. Payload-less tombstones are always accepted, but only update items the server already has (see "Oversized items").

## Other recovery

- Worker health (`SyncWorkerHealthMonitor.ts`) sends a 15s ping and treats a 30s silence as a timeout. A crashed worker is auto-restarted until `MAX_CONSECUTIVE_CRASHES` (3) crashes in a row, and an unresponsive one until `MAX_CONSECUTIVE_TIMEOUTS` (5) timeouts in a row, each count resetting after a minute without one. Then sync stops and the user is asked to refresh.
- **The manifest sync is a phase of the poll.** `SyncPoller.executePoll` is a fixed pipeline: a `beforeRead` manifest phase, which runs a sync only for a demand that must come before the read (catch-up); the push and the read; an `afterRead` phase for any other demand, request, ticket or periodic sync; then healing and snapshot uploads. So the manifest sync shares the poll's leadership, online state, abort, auth pause and backoff, and never overlaps a push or an upload. A manifest that can't be fetched throws, which fails the poll (rule 4), and so does a snapshot request (or the upload before the manifest) that fails as a whole: an outage, a 5xx, a rejected session or an outdated build (`isRequestFailure`). Items that fail on their own don't: a server that defers every item, a snapshot that won't decrypt or hydrate, or a missing key only leaves the sync incomplete, so one broken item can't block sync.
  - **When it runs.** The orchestrator asks for one (`request('due')`) on promotion, on coming back online and when the user comes back to a tab (`onForeground`), and the request stays until a sync fetches the manifest. Otherwise it's due `manifestSyncMinGap` (50 min) after the last clean sync, or `manifestSyncInterval` (1 h) after the last one that fetched the manifest, whichever is later, so a sync with item failures retries hourly rather than at every poll. `getDueAt` brings the next poll forward to that time (`manifestDueAt` in `pollSchedule`), never past failure backoff. A demand is due at once too. A sync that runs serves everything asked for when it started, so a poll runs at most one manifest sync: one for catch-up meets a recovery demand and makes the periodic one not due.
  - **Modes.** `due` is skipped within `manifestSyncMinGap` of the last clean sync unless the device has no items; `now` (catch-up, recovery) ignores the gap; `force` (full resync, `replaceFromServer`) also fetches quarantined items and every newer copy. A caller that needs the result (`bootstrapItems`, `fullResync`, `replaceFromServer`) opens a ticket and runs a poll (`SyncOrchestrator.syncManifest`), after the one in flight; a poll that ends without serving it returns a failure and leaves nothing asked for.
